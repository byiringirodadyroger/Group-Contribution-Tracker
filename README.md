# Group Contribution Tracker

A full-stack contribution tracker that starts with six member profiles. Each
profile has a fixed target of **20,000 RWF**; Roger can add more profiles from
Administration when additional members join.
Members create an account for their group profile, sign in to request access,
and must be approved by Roger before they can view group data.

## Project layout

- `server/` — Express, Mongoose, JWT-cookie authentication, access control,
  payment history, audit logging, and authenticated Socket.IO updates.
- `client/` — React/Vite dashboard and member-facing pages.

See [server/README.md](./server/README.md) for API details and deployment
configuration, and [client/README.md](./client/README.md) for frontend setup.

## Run locally (Windows PowerShell)

### 1. Configure and start the API

Use Node.js 20 or newer. Start MongoDB locally or create a MongoDB Atlas
database, then configure the connection string and fresh secrets:

```powershell
Set-Location server
npm.cmd install
Copy-Item .env.example .env
notepad .env
```

In `server/.env`, set `MONGODB_URI`, generate independent random values of at
least 32 characters for `JWT_SECRET` and `BOOTSTRAP_SETUP_SECRET`, and use
`CORS_ORIGINS=http://localhost:5173` for the Vite development server. Never
commit `.env`.

Start the API:

```powershell
npm.cmd run dev
```

The API listens on `http://localhost:4000`. Keep it running.

### 2. Create the initial administrator and group profiles

In a second PowerShell window, enter the bootstrap secret and choose a strong,
unique password for Roger. The setup endpoint runs only once and refuses a
non-empty database.

```powershell
$setupSecretSecure = Read-Host "Bootstrap setup secret" -AsSecureString
$setupSecretPointer = [Runtime.InteropServices.Marshal]::SecureStringToBSTR($setupSecretSecure)
$adminEmail = Read-Host "Admin email address"
$adminPasswordSecure = Read-Host "New Roger administrator password" -AsSecureString
$adminPasswordPointer = [Runtime.InteropServices.Marshal]::SecureStringToBSTR($adminPasswordSecure)
try {
    $setupSecret = [Runtime.InteropServices.Marshal]::PtrToStringBSTR($setupSecretPointer)
    $adminPassword = [Runtime.InteropServices.Marshal]::PtrToStringBSTR($adminPasswordPointer)
    $body = @{ username = $adminEmail; adminPassword = $adminPassword } | ConvertTo-Json
    Invoke-RestMethod -Method Post `
        -Uri "http://localhost:4000/api/auth/setup/bootstrap" `
        -Headers @{ "X-Setup-Secret" = $setupSecret } `
        -ContentType "application/json" -Body $body
}
finally {
    [Runtime.InteropServices.Marshal]::ZeroFreeBSTR($setupSecretPointer)
    [Runtime.InteropServices.Marshal]::ZeroFreeBSTR($adminPasswordPointer)
    Remove-Variable adminEmail, adminPassword, adminPasswordSecure, setupSecret, setupSecretSecure -ErrorAction SilentlyContinue
}
```

After successful setup, remove `BOOTSTRAP_SETUP_SECRET` from `server/.env` and
restart the API. Roger signs in with the email address configured above and the
password entered at the prompt. Login also accepts usernames. No production
password is supplied or stored in the source.

### 3. Start the frontend

```powershell
Set-Location ..\client
npm.cmd install
npm.cmd run dev
```

Open the Vite URL shown in the terminal (normally `http://localhost:5173`).
Roger can approve member account requests from **Administration**. Each regular
member selects their matching name when creating an account.
After signing in, they must submit an access request; group data remains
inaccessible until Roger approves it.

## Deploy to Render

`render.yaml` deploys both services from this repository: the API (`server/`,
a Node web service) and the dashboard (`client/`, a static site). MongoDB is
not hosted by Render, so use MongoDB Atlas.

1. **Database.** Create an Atlas cluster and a database user with a strong
   password. Under *Network Access*, allow connections from Render. `0.0.0.0/0`
   is the simple option; keep database credentials strong and private. Copy the
   `mongodb+srv://...` connection string and include a database name, for example
   `.../group_contribution_tracker`.
2. **Push** this repository to GitHub. Never commit `server/.env`.
3. **Create the Blueprint.** In Render choose **New > Blueprint**, select the
   repository, and let Render read `render.yaml`. It prompts for:
   - `MONGODB_URI`: the Atlas connection string from step 1.
   - `CORS_ORIGINS`: the exact frontend origin, initially expected to be
     `https://group-contribution-tracker-web.onrender.com`.
   - `VITE_API_URL`: the API origin, initially expected to be
     `https://group-contribution-tracker-api.onrender.com`.

   `JWT_SECRET` and `BOOTSTRAP_SETUP_SECRET` are generated by Render.
4. **Check the real URLs.** If either service name was already taken, Render
   may add a suffix to its URL. Compare the actual URLs in the Render dashboard.
   If they differ, correct `CORS_ORIGINS` on the API and `VITE_API_URL` on the
   static site, then redeploy the static site (`VITE_API_URL` is baked in at
   build time).
5. **Run one-time setup** against the API URL using the bootstrap instructions
   above. Read `BOOTSTRAP_SETUP_SECRET` from the API service's Environment tab.
   After setup succeeds, remove that variable.
6. Test sign-in, access approval, adding a payment, and live updates before
   sharing the frontend URL.

Notes:

- `ALLOWED_IPS` is deliberately not set in the Blueprint: member IPs can change,
  so an allowlist can lock them out. Configure it only if you need it.
- The Blueprint uses Render's free plan. A free API sleeps after inactivity, so
  its first request afterwards may be slow. Change `plan: free` to
  `plan: starter` in `render.yaml` to keep it awake.
- The two `onrender.com` services are on separate sites, so the Blueprint sets
  `COOKIE_SAME_SITE=none`. Browsers that block third-party cookies (notably
  Safari on iPhone) may not keep users signed in. For reliable cookies, use
  custom frontend/API subdomains under one parent domain, such as
  `app.example.com` and `api.example.com`, set `COOKIE_SAME_SITE=lax`, update
  `CORS_ORIGINS` and `VITE_API_URL`, then redeploy.
- Keep payment writes restricted to the approved administrator; the API
  enforces this independently of the frontend.
